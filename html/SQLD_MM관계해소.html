💡 1과목 심화: M:M 관계 해소 완벽 이해

현실 세계의 다대다(M:M) 관계가 왜 데이터베이스에서는 구현 불가능한지,
그리고 '교차 엔터티'가 이를 어떻게 구원하는지 테이블 구조로 확인합니다.

1. 문제 발생: M:M을 그대로 물리 DB로 만들면?

현실 세계(개념적 모델링)에서는 "학생 여러 명이 과목 여러 개를 듣는다"가 너무 자연스럽습니다.

[학생]
───∈ ∋───
[과목]

하지만 이걸 오라클이나 MySQL 같은 실제 데이터베이스(물리 DB) 테이블로 그대로 만들려고 하면 치명적인 버그(제1정규형 위배)가 발생합니다.

❌ 실패한 [학생] 테이블 구조

학번(PK)이름수강과목코드(FK)
101옥한빛DB01, JA02, CS03
102이태연JA02, CS03

➔ 속성(칸) 하나에는 무조건 1개의 값만 들어가야 하는데(원자성), 쉼표(,)로 여러 개를 우겨 넣게 되어 DB가 망가집니다.

❌ 실패한 [과목] 테이블 구조

과목코드(PK)과목명수강학생학번(FK)
JA02자바101, 102, 105...

➔ 반대쪽도 마찬가지입니다. 하나의 과목에 수십 명의 학생 학번을 넣을 공간이 없습니다.

2. 해결책: 다리(Bridge)를 놓아라! (교차 엔터티)

직접 연결을 포기하고, 가운데에 새로운 테이블(교차 엔터티/행위 엔터티)을 하나 파서 양쪽을 연결하는 징검다리 역할을 맡깁니다. 이 다리의 이름이 바로 [수강내역]입니다.

[학생]
───|초
⭐ [수강내역] ⭐
O|───
[과목]

M:M (다대다) 관계 ➔ 1:M (일대다) 관계 2개로 쪼개짐!

✅ 성공적인 물리적 DB 테이블 구조

이제 각 테이블은 원자성을 지키면서도 완벽하게 수강 정보를 관리할 수 있게 되었습니다.

1. 순수한 [학생] 테이블 (1)
학번(PK)이름
101옥한빛
102이태연
2. 교차 엔터티 [수강내역] 테이블 (M)
학번 (FK)과목코드 (FK)신청일자 (추가속성)
101DB012026-03-02
101JA022026-03-02
102JA022026-03-03

➔ 학생 테이블의 학번과 과목 테이블의 과목코드를 둘 다 빌려와서(FK) 연결 고리로 씁니다. ('학번+과목코드'를 묶어서 이 테이블의 PK로 쓰기도 합니다 = 식별자 관계)

3. 순수한 [과목] 테이블 (1)
과목코드(PK)과목명
DB01데이터베이스
JA02자바 프로그래밍

🎯 실전 기출 지문 암기

  • ✅ "M:M 관계는 데이터 모델링의 논리적/물리적 단계에서 구현할 수 없으므로 해소해야 한다." (O)
  • ✅ "M:M 관계를 해소하기 위해 새로운 교차 엔터티(관계 엔터티)를 추가한다." (O)
  • ✅ "M:M 관계는 교차 엔터티를 통해 두 개의 1:M 관계로 분리된다." (O)
