📖 주제 10: 인덱스(Index)의 구조와 원리

B-Tree 인덱스는 도대체 어떻게 생겼길래 검색이 빠른 걸까?
그리고 왜 데이터가 너무 많으면 인덱스를 버리는 게 나을까?

1. B-Tree (Balanced Tree)의 비밀

오라클(Oracle)을 비롯한 대부분의 관계형 DB가 사용하는 기본 인덱스 구조입니다. 여기서 'B'는 Binary가 아니라 Balanced(균형 잡힌)를 뜻합니다. 어디를 찾든 탐색 시간이 동일하도록 트리 깊이를 밸런싱합니다.

[Root Block - 뿌리]
100 ~ 500은 왼쪽 / 501 ~ 999는 오른쪽
↙                      ↘
[Branch Block - 가지]
100 ~ 300 / 301 ~ 500
501 ~ 700 / 701 ~ 999
↙   ↘                            ↙   ↘
[Leaf Block - 잎사귀 (데이터의 실제 주소)]
키값(100) + ROWID
키값(301) + ROWID
키값(501) + ROWID
키값(701) + ROWID

💡 핵심 개념: ROWID (로우 아이디)

인덱스의 맨 마지막(Leaf Block)에는 정렬된 '인덱스 키값'과 함께 'ROWID'가 저장되어 있습니다.
ROWID는 실제 테이블 데이터가 디스크의 어느 파일, 어느 블록에 저장되어 있는지 알려주는 '물리적 주소(포인터)'입니다.

2. 인덱스 스캔의 3가지 방식 (기출 포인트)

실행 계획을 까보면(EXPLAIN PLAN) 자주 등장하는 인덱스 스캔의 종류입니다.

스캔 방식 특징 및 발생 조건
Index Unique Scan
(단일 건 스캔)		 가장 빠릅니다. PK(기본키)나 Unique 인덱스로 생성된 컬럼을 = (동등 조건)으로 검색할 때 발생합니다.
➔ 무조건 데이터가 1건만 존재함을 DB가 확신할 수 있기 때문입니다.
Index Range Scan
(범위 스캔)		 가장 일반적인 스캔입니다. 인덱스를 타긴 타는데, 수직으로 탐색한 뒤 Leaf Block에서 조건에 맞는 곳까지 수평으로 쭈욱(Range) 읽어 나갑니다.
➔ BETWEEN, LIKE '옥%', > 등을 쓸 때, 또는 중복이 허용된 일반 인덱스를 =로 검색할 때 발생합니다.
Index Full Scan
(전체 스캔)		 테이블은 안 읽고 인덱스의 Leaf Block만 처음부터 끝까지 다 읽는 방식입니다.
➔ 쿼리에서 요구하는 컬럼들이 모두 인덱스에 포함되어 있어서, 굳이 무거운 테이블까지 갈 필요가 없을 때 발생합니다.

3. 무조건 인덱스가 빠를까? (손익 분기점)

이 개념이 시험에서 가장 헷갈리게 나오는 단골 함정입니다. "인덱스가 무조건 Table Full Scan보다 빠르다?" ➔ ❌ (틀린 보기)

🚨 인덱스의 손익 분기점 (Break-Even Point)

인덱스를 타면 인덱스 블록 읽기 ➔ ROWID 확인 ➔ 테이블 블록 읽기 과정을 거치며 '랜덤 액세스(Random Access)'가 발생합니다. 데이터를 하나씩 건건이 찔러보는 방식이죠.

만약 테이블 전체 데이터의 약 15~20% 이상을 읽어야 한다면 어떻게 될까요?
차라리 인덱스를 포기하고 Table Full Scan(한 번에 여러 블록을 뭉텅이로 읽어 들이는 Multi-block I/O)을 하는 것이 디스크 효율 상 훨씬 빠릅니다!

➔ 옵티마이저(CBO)는 이 통계를 계산해서 "아, 추출할 데이터가 너무 많네. 인덱스 버려!" 하고 스스로 Table Full Scan을 선택합니다.
