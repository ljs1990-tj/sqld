🚨 실전 SQL 쿼리: 인덱스 스캔 분석

어떤 조건에서 Unique Scan이 터지고, Range Scan이 터지는지,
그리고 왜 옵티마이저는 멀쩡한 인덱스를 버리는지 확인합니다.

1. Unique Scan vs Range Scan

STUDENT 테이블의 stu_no(학번)는 PK(기본키)이며, stu_dept(학과)에는 일반 인덱스가 걸려있다고 가정합니다.

INDEX UNIQUE SCAN
-- PK 컬럼을 동등(=) 조건으로 단 1건만 정확히 찌름
SELECT * FROM student WHERE stu_no = '20153075';
Execution Plan
---------------------------------------------------
0 SELECT STATEMENT
1   TABLE ACCESS (BY INDEX ROWID) OF 'STUDENT'
2     INDEX (UNIQUE SCAN) OF 'PK_STUDENT'

➔ 분석: 학번은 중복될 수 없는 PK입니다. DB는 '옥한빛' 1명을 찾자마자 뒤도 돌아보지 않고 즉시 검색을 종료합니다. 가장 빠른 스캔입니다.

INDEX RANGE SCAN
-- 중복이 가능한 일반 인덱스 컬럼을 동등(=) 조건으로 검색
SELECT * FROM student WHERE stu_dept = '기계';
Execution Plan
---------------------------------------------------
0 SELECT STATEMENT
1   TABLE ACCESS (BY INDEX ROWID) OF 'STUDENT'
2     INDEX (RANGE SCAN) OF 'IDX_STUDENT_DEPT'

➔ 분석: '기계과' 학생은 여러 명일 수 있습니다. 인덱스를 타고 기계과가 시작하는 첫 위치를 찾은 다음, 기계과 데이터가 끝날 때까지 수평으로 쭈욱(Range) 훑으며 검색합니다.

2. 인덱스의 손익 분기점 (왜 인덱스를 버리는가?)

PK(학번) 인덱스가 완벽하게 살아있는데도 불구하고, 옵티마이저가 스스로 인덱스를 포기하는 순간입니다.

TABLE FULL SCAN
-- 학번이 0보다 큰 모든 학생을 조회 (사실상 100% 전체 데이터)
SELECT * FROM student WHERE stu_no > '00000000';
Execution Plan
---------------------------------------------------
0 SELECT STATEMENT
1   TABLE ACCESS (FULL) OF 'STUDENT'

➔ 분석: 옵티마이저의 판단은 이렇습니다.
"어차피 전교생 데이터를 다 꺼내달라는 거네? 이거 인덱스 타면 인덱스 블록 방문 ➔ 테이블 블록 방문을 10번(랜덤 액세스) 반복해야 하잖아? 너무 비효율적이야. 그냥 테이블 디스크 1페이지부터 끝까지 한방에 확 긁어오는(Full Scan) 게 낫겠다!"
