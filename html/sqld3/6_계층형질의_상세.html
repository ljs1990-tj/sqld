🌳 계층형 질의 & Top N 쿼리 심층 분석

트리(Tree) 순회 방향의 원리와 ROWNUM 실행 순서 버그의 진짜 이유를 파헤칩니다.

📋 [베이스 데이터] 사원(EMP) 테이블 구조

모든 계층형 쿼리는 '자신의 PK'와 '부모를 가리키는 FK'가 한 테이블 안에 있을 때 성립합니다.

사번 (EMP_NO)이름 (EMP_NAME)매니저사번 (MGR_NO)
100나사장NULL
101김팀장100
102박팀장100
103이사원101

1. PRIOR의 진짜 의미 (순방향 vs 역방향)

개발자 입장에서 PRIOR는 "방금 전 루프(Loop)에서 읽은 데이터"를 뜻하는 포인터(Pointer) 예약어입니다.

⬇️ 순방향 (Top-Down): "내 부하직원 찾아라!"

SELECT LEVEL, 사번, 이름, 매니저사번
FROM 사원
START WITH 매니저사번 IS NULL -- 1. [Root] 나사장을 먼저 짚는다. (LEVEL 1)
CONNECT BY PRIOR 사번 = 매니저사번;
💡 데이터베이스의 내부 동작 (해석):
  1. 나사장을 읽는다. 나사장의 사번은 100이다.
  2. CONNECT BY를 만난다. "방금 읽은(PRIOR) 사번(100)이 매니저사번인 놈들을 찾아!"
  3. 매니저사번이 100인 '김팀장', '박팀장'을 데려온다. (얘네가 LEVEL 2)
  4. 김팀장을 읽는다. 김팀장의 사번은 101이다.
  5. 다시 "방금 읽은(PRIOR) 사번(101)이 매니저사번인 놈을 찾아!" ➔ '이사원' 데려옴 (LEVEL 3)

➔ 결론: 위에서 아래로 파고드는 순방향 전개가 됨!

⬆️ 역방향 (Bottom-Up): "내 상사를 찾아라!"

SELECT LEVEL, 사번, 이름, 매니저사번
FROM 사원
START WITH 이름 = '이사원' -- 1. [Root] 맨 밑단 이사원을 짚는다. (LEVEL 1)
CONNECT BY PRIOR 매니저사번 = 사번;
💡 데이터베이스의 내부 동작 (해석):
  1. 이사원을 읽는다. 이사원의 매니저사번은 101이다.
  2. CONNECT BY를 만난다. "방금 읽은(PRIOR) 매니저사번(101)이 본인의 사번인 놈을 찾아!"
  3. 사번이 101인 '김팀장'을 데려온다. (얘가 LEVEL 2)
  4. 김팀장을 읽는다. 김팀장의 매니저사번은 100이다.
  5. 다시 "방금 읽은(PRIOR) 매니저사번(100)이 본인의 사번인 놈을 찾아!" ➔ '나사장' 데려옴 (LEVEL 3)

➔ 결론: 아래에서 위로 거슬러 올라가는 역방향 전개가 됨!

2. Top N 쿼리와 ROWNUM 실행 순서의 함정

게시판 페이징이나 상위 N개 추출 시 오라클에서는 ROWNUM(데이터가 추출되는 순서대로 부여되는 가짜 일련번호)을 씁니다. 여기서 실무/시험 공통으로 가장 많이 터지는 버그가 있습니다.

❌ 치명적 논리 오류: 정렬(ORDER BY)의 배신

SELECT 이름, 키
FROM 학생
WHERE ROWNUM <= 3
ORDER BY 키 DESC;

[디버깅 리포트]

SQL의 실행 순서는 FROM ➔ WHERE ➔ SELECT ➔ ORDER BY 입니다.
데이터베이스는 키 순서대로 줄을 세운 다음 3명을 뽑는 게 아니라,
WHERE절에서 테이블에 저장된 순서대로 아무나 3명을 덜컥 뽑아버립니다(ROWNUM).
그리고 나서 맨 마지막에 ORDER BY를 만나 그 3명 안에서만 순서를 정렬합니다. ➔ 원하는 결과(Top 3)가 절대 안 나옴!

✅ 해결책: 인라인 뷰(Inline View)를 이용한 강제 정렬

이 문제를 해결하려면 서브쿼리(인라인 뷰)를 만들어 정렬(ORDER BY)을 가장 먼저 강제로 실행시켜야 합니다.

SELECT * FROM (
    SELECT 이름, 키
    FROM 학생
    ORDER BY 키 DESC -- 1. 무조건 줄부터 세워서 완벽한 표(가상 테이블)를 만든다!
)
WHERE ROWNUM <= 3; -- 2. 완벽히 정렬된 표의 윗부분에서 3칸을 썰어낸다!
