🧠 대망의 마지막: 옵티마이저와 인덱스

DB의 두뇌인 옵티마이저가 쿼리를 어떻게 해석하는지 이해하고,
개발자의 영원한 숙제인 '인덱스(Index) 튜닝'의 핵심 원리를 완벽하게 정리합니다.

1. 옵티마이저 (Optimizer): DB의 내비게이션

개발자가 SQL을 작성해서 던지면, DB 내부에서 "이 쿼리를 어떤 순서로, 어떤 인덱스를 타서 가져오는 게 가장 빠를까?"를 계산하고 실행 계획(Execution Plan)을 세워주는 핵심 두뇌입니다.

규칙 기반 (RBO: Rule-Based)

  • 과거의 방식 (현재는 거의 안 씀)
  • 미리 정해놓은 15개의 우선순위 규칙에 따라 무조건 기계적으로 경로를 선택.
  • 예: "인덱스가 있으면 무조건 인덱스를 탄다!" (데이터가 10건밖에 없어도 무식하게 인덱스를 탐)

비용 기반 (CBO: Cost-Based)

  • 현대의 표준 방식 (실무/시험의 중심)
  • 테이블의 통계 정보(데이터 수, 분포도 등)를 분석하여 가장 비용(시간/메모리)이 적게 드는 경로를 지능적으로 선택.
  • 예: "인덱스가 있긴 한데, 전체 데이터의 80%를 읽어야 하네? 차라리 인덱스 버리고 테이블 전체를 스캔하는 게 낫겠다!"

2. 테이블 풀 스캔 vs 인덱스 스캔

인덱스는 두꺼운 전공 서적 맨 뒤에 있는 '찾아보기(색인)'와 완벽하게 똑같습니다.

Table Full Scan (테이블 전체 스캔) Index Range Scan (인덱스 스캔)
"책의 1페이지부터 끝까지 다 넘기면서 찾기"

데이터가 아주 적거나, 전체 데이터의 대부분(보통 15~20% 이상)을 읽어야 할 때 옵티마이저가 스스로 선택합니다. (무조건 나쁜 것이 아닙니다!) 		"맨 뒤 찾아보기에서 페이지 번호를 확인하고 바로 펴기"

B-Tree(Tree 구조)로 정렬되어 있어 특정 소수의 데이터를 아주 빠르게 찾을 때 유리합니다.
PK(기본키)를 생성하면 자동으로 인덱스가 생성됩니다.

3. 기출 0순위: 인덱스를 바보로 만드는 실수들

시험에 무조건 출제됩니다! 인덱스가 버젓이 존재하는데도, 개발자가 쿼리를 잘못 짜서 옵티마이저가 인덱스를 포기하고 Table Full Scan을 해버리는 치명적인 경우들입니다.

❌ 1. 인덱스 컬럼을 함수나 연산자로 가공할 때

찾아보기(인덱스)는 '옥한빛'으로 정렬되어 있는데, 쿼리에서 이름을 잘라버리면 찾을 수가 없습니다.

-- 오답 (인덱스 못 탐): 컬럼 자체를 건드림
SELECT * FROM student WHERE SUBSTR(stu_name, 1, 1) = '옥';

-- 정답 (인덱스 탐): 컬럼은 가만히 냅둠
SELECT * FROM student WHERE stu_name LIKE '옥%';

❌ 2. 묵시적(암시적) 형변환이 일어날 때

학번(stu_no)이 문자형(VARCHAR)인데 숫자형으로 검색하면, DB가 몰래 TO_NUMBER(stu_no)로 컬럼을 가공해버려서 인덱스가 깨집니다.

-- 오답 (인덱스 못 탐): 문자를 숫자로 비교함
SELECT * FROM student WHERE stu_no = 20153075;

-- 정답 (인덱스 탐): 타입 일치시킴
SELECT * FROM student WHERE stu_no = '20153075';

❌ 3. LIKE 검색 시 와일드카드(%)가 앞에 있을 때

사전에서 '한빛'으로 끝나는 단어를 찾으려면 처음부터 다 뒤져야 하는 것과 같은 이치입니다.

-- 오답 (인덱스 못 탐): %가 앞에 있음
SELECT * FROM student WHERE stu_name LIKE '%한빛';
