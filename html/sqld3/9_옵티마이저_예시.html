🚨 실전 SQL 쿼리: 인덱스 무효화의 함정

인덱스가 잘 걸려 있음에도 불구하고,
개발자의 쿼리 작성 실수로 데이터베이스가 전체 스캔을 해버리는 상황을 비교합니다.

1. 타입 불일치 (암시적 형변환)

STUDENT 테이블의 학번(stu_no)은 CHAR(8), 즉 문자형입니다. (제공해주신 스키마 기준)

Worst (Table Full Scan)
-- 학번(문자형)에 숫자 값을 그대로 넣어서 검색함
SELECT * FROM student
WHERE stu_no = 20153075;
[실행 계획 분석]
DB 옵티마이저: "어? 컬럼은 문자인데 숫자가 들어왔네? 내가 알아서 문자를 숫자로 바꿔서 비교해야겠다."
➔ 내부적으로 TO_NUMBER(stu_no) = 20153075 로 변환됨.
➔ 인덱스 컬럼 자체(stu_no)가 가공되었으므로 인덱스 사용 불가! (전체 스캔)
Best (Index Range Scan)
-- 학번 데이터 타입에 맞춰 양쪽에 따옴표를 붙여 문자형으로 검색함
SELECT * FROM student
WHERE stu_no = '20153075';
[실행 계획 분석]
DB 옵티마이저: "타입이 완벽하게 일치하군! PK 인덱스를 타고 바로 1건만 가져오자."
➔ 0.001초 만에 검색 완료!

2. 인덱스 컬럼에 함수 사용 (가공)

이름(stu_name) 컬럼에 인덱스가 걸려있다고 가정해 봅시다. '옥'씨 성을 가진 학생을 찾으려 합니다.

Worst (Table Full Scan)
-- SUBSTR 함수로 원본 컬럼(stu_name)을 훼손함
SELECT * FROM student
WHERE SUBSTR(stu_name, 1, 1) = '옥';
[실행 계획 분석]
인덱스라는 책의 색인은 원본 이름(옥한빛)으로 정리되어 있습니다.
그런데 원본 컬럼에 SUBSTR() 함수를 씌우는 순간, DB는 색인을 포기하고 1페이지부터 끝까지 다 뒤지면서 성씨를 자르고 비교하기 시작합니다.
Best (Index Range Scan)
-- 원본 컬럼은 가만히 두고, LIKE 연산자를 활용함
SELECT * FROM student
WHERE stu_name LIKE '옥%';
[실행 계획 분석]
DB 옵티마이저: "원본 컬럼이 그대로 유지되어 있네. 인덱스에서 '옥'으로 시작하는 부분만 빠르게 읽고 빠지자!"

3. LIKE 검색 시 앞쪽 와일드카드(%) 사용

이름이 '한빛'으로 끝나는 학생을 찾고 싶을 때 발생하는 일입니다.

Worst (Table Full Scan)
-- 와일드카드(%)가 맨 앞에 옴
SELECT * FROM student
WHERE stu_name LIKE '%한빛';
[실행 계획 분석]
종이 국어사전에서 "무슨 글자든 상관없고, 뒤가 '한빛'으로 끝나는 단어를 찾아라" 라고 하면 어떨까요?
사전의 'ㄱ'부터 'ㅎ'까지 첫 페이지부터 끝 페이지까지 모조리 눈으로 읽어야 합니다.
DB도 마찬가지로 %가 맨 앞에 오면 인덱스를 포기하고 Table Full Scan을 해버립니다.
