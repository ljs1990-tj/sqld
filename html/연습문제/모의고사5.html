📚 제 1과목 : 데이터 모델링의 이해 (10문제)
Q01. 다음 중 데이터 모델이 제공하는 3가지 핵심 요소에 해당하지 않는 것은?
  • ① 데이터 구조 및 정의 (Structure)
  • ② 데이터 연산 (Operation)
  • ③ 데이터 흐름도 (Data Flow Diagram)
  • ④ 제약조건 (Constraint)
상세 해설
정답은 ③입니다.
  • ①, ②, ④ (옳은 선지): 데이터 모델의 3대 요소는 **구조(Structure)**, **연산(Operation)**, **제약조건(Constraint)**입니다.
  • ③ 데이터 흐름도 (틀린 선지): 구조적 분석 방법론에서 프로세스의 흐름을 다루는 도구이며, 데이터 모델 자체의 핵심 구성 요소에 포함되지 않습니다.
Q02. 엔터티(Entity) 간의 관계(Relationship)를 정의할 때 고려해야 할 '관계의 3대 요소'가 올바르게 짝지어진 것은?
  • ① 관계명(Name), 관계차수(Cardinality), 관계선택사양(Optionality)
  • ② 식별성(Identity), 결정자(Determinant), 종속성(Dependency)
  • ③ 존재성(Existence), 행위성(Action), 원자성(Atomicity)
  • ④ 유일성(Uniqueness), 최소성(Minimality), 불변성(Invariability)
상세 해설
정답은 ①입니다.
  • ① (옳은 선지): 엔터티 간 관계를 구성하는 3대 요소는 관계의 이름인 **관계명**, 수량 한계를 뜻하는 **관계차수(1:1, 1:M 등)**, 필수 여부를 뜻하는 **관계선택사양(필수/선택)**입니다.
  • ④ (틀린 선지): 유일성, 최소성, 불변성은 관계가 아니라 '주식별자'의 도출 기준 특징입니다.
Q03. 다음 중 속성(Attribute)의 정의와 특징에 대한 설명으로 가장 올바르지 않은 것은?
  • ① 속성은 엔터티가 관리하는 가장 작은 논리적 단위로서, 의미적으로 더 이상 쪼개질 수 없어야 한다.
  • ② 하나의 인스턴스(행)에서 하나의 속성은 반드시 단 한 개의 값(원자값)만을 가져야 한다.
  • ③ 주식별자에 종속되지 않고 일반 속성들끼리 종속 관계를 가지는 구조는 정상적인 데이터 모델이므로 분리할 필요가 없다.
  • ④ 하나의 엔터티는 구체적인 성격을 나타내는 일반 속성과 유일성을 보장하는 식별자 속성으로 구성된다.
상세 해설
정답은 ③입니다.
  • ①, ②, ④ (옳은 선지): 속성의 기본 정의(최소 논리 단위, 원자값 보유)와 구성을 정확히 서술했습니다.
  • ③ 일반 속성들끼리 종속 관계를 가지는 구조... 분리할 필요가 없다 (틀린 선지): 일반 속성이 다른 일반 속성을 결정짓는 구조를 '이행 함수 종속'이라고 하며, 이는 제3정규화(3NF)를 통해 반드시 별도의 엔터티로 분리해주어야 데이터 이상현상을 방지할 수 있습니다.
Q04. 다음 중 식별자(Identifier)의 대체 여부에 따른 분류에 해당하는 용어로만 짝지어진 것은?
  • ① 주식별자, 보조식별자
  • ② 내부식별자, 외부식별자
  • ③ 본질식별자, 인조식별자
  • ④ 단일식별자, 복합식별자
상세 해설
정답은 ③입니다.
  • 식별자의 분류 기준은 자주 출제되는 단골 영역입니다.
  • ① 주식별자, 보조식별자: 대표성 여부에 따른 분류
  • ② 내부식별자, 외부식별자: 스스로 생성되었는지 여부(엔터티 내 생성 여부)에 따른 분류
  • ③ 본질식별자, 인조식별자 (옳은 선지): 대체 여부(원래 존재하던 본질 식별자를 인위적인 인조 식별자로 대체할 수 있는지)에 따른 분류
  • ④ 단일식별자, 복합식별자: 속성 수에 따른 분류
Q05. 부모 엔터티의 주식별자를 자식 엔터티의 일반 속성(외래키)으로만 전송하고, 자식의 주식별자 영역에는 포함시키지 않는 관계 표기법은?
  • ① 식별자 관계 (Identifying Relationship)
  • ② 비식별자 관계 (Non-Identifying Relationship)
  • ③ 재귀적 관계 (Recursive Relationship)
  • ④ 다대다 관계 (Many-to-Many Relationship)
상세 해설
정답은 ② 비식별자 관계입니다.
  • 부모의 PK를 일반 속성 영역으로 상속받아 단순 참고용 외래키(FK)로만 엮는 결합 구조를 비식별자 관계라고 하며, ERD 표기법 상 점선으로 나타냅니다.
  • 반면 자식의 주식별자(PK) 결합 키 중 하나로 포함시키는 형태는 식별자 관계(실선 표현)입니다.
Q06. 데이터 모델의 가독성과 유지보수성을 극대화하기 위해 수행하는 정규화(Normalization)의 효과로 가장 거리가 먼 것은?
  • ① 엔터티 내부의 데이터 중복을 원천적으로 차단하여 저장 공간을 효율화한다.
  • ② 데이터의 입력, 수정, 삭제(DML)가 발생할 때 나타날 수 있는 결정자/종속자 간의 이상현상을 방지한다.
  • ③ 정규화를 거치면 테이블이 세부적으로 쪼개지므로 대량의 조인(Join) 쿼리 수행 시 조회 성능이 항상 비약적으로 상승한다.
  • ④ 주제 중심의 독립적인 엔터티 구조가 확립되어 향후 비즈니스 요구사항 변경 시 모델의 유연성이 높아진다.
상세 해설
정답은 ③입니다.
  • ①, ②, ④ (옳은 선지): 데이터 중복 제거, 무결성 확보, 유연성 증대 등은 정규화가 주는 본질적인 이점입니다.
  • ③ 정규화를 거치면 조회 성능이 항상 비약적으로 상승 (틀린 선지): 정규화를 수행하면 테이블이 세분화되어 쪼개지므로, 데이터를 모아서 조회할 때 필연적으로 많은 조인(Join)을 유발하게 됩니다. 과도한 조인은 CPU 부하 및 디스크 I/O를 증가시켜 오히려 조회(SELECT) 성능을 저하시키는 주원인이 될 수 있습니다. (이 때문에 반정규화를 고려하게 됩니다.)
Q07. 다음 중 제3정규형(3NF)을 만족하는 데이터 모델에서 후보키(Candidate Key)가 아닌 결정자(Determinant)가 존재하여, 이를 제거함으로써 결정자가 모두 후보키가 되도록 강제하는 정규화 단계는?
  • ① 제2정규형 (2NF)
  • ② 보이스-코드 정규형 (BCNF)
  • ③ 제4정규형 (4NF)
  • ④ 제5정규형 (5NF)
상세 해설
정답은 ② 보이스-코드 정규형 (BCNF)입니다.
  • 3정규형을 완료한 모델에서 복합키 주식별자의 일부를 일반 속성이 결정짓는 특수 케이스가 생길 수 있습니다. 이때 "모든 결정자는 후보키여야 한다"는 규칙을 적용해 분리하는 정규형 단계를 BCNF라고 부릅니다.
Q08. 반정규화(Denormalization) 프로세스 중 성능 개선 대안을 검토하는 단계에서 최우선으로 고려해야 할 사항으로 가장 올바르지 않은 것은?
  • ① 자주 조회되는 컬럼들을 모아 성능을 최적화할 수 있도록 대량의 인덱스(Index)를 우선 추가한다.
  • ② 데이터 접근 경로를 단축하거나 임시 결과 집합을 저장하기 위해 뷰(View) 테이블 도입을 검토한다.
  • ③ 대량의 데이터 범위 스캔 시 디스크 블록 밀집도를 높이기 위해 클러스터링(Clustering) 기법 적용을 검토한다.
  • ④ 애플리케이션 단계에서 로직을 변경하거나 메모리 캐싱(Caching) 레이어를 도입하여 DB 서버의 부하를 줄일 수 있는지 확인한다.
상세 해설
정답은 ①입니다.
  • ②, ③, ④ (옳은 선지): 반정규화는 데이터 무결성을 파괴할 위험이 큰 최후의 수단이므로, 적용 전에 반드시 뷰 도입, 클러스터링 기법, 앱 로직 튜닝 등을 선행 검토해야 합니다.
  • ① 대량의 인덱스를 우선 추가한다 (틀린 선지): 인덱스는 조회 성능을 높여주지만, 무분별하게 과도한 인덱스를 추가하면 데이터 입력/수정/삭제(DML) 시 인덱스 트리를 재정렬하느라 시스템 성능이 심각하게 마비됩니다. 튜닝 관점에서 무조건 대량 인덱스를 추가하는 것은 올바른 선행 대안이 아닙니다.
Q09. 분산 데이터베이스(Distributed Database)의 장점과 단점에 대한 설명 중 가장 적절하지 않은 것은?
  • ① 지역별로 데이터를 분산하여 처리하므로 시스템의 지역 자치성과 유연성이 증대된다.
  • ② 특정 지역 노드에 장애가 발생하더라도 전체 시스템이 마비되지 않고 다른 노드를 통해 서비스 지속이 가능한 생존성(장애 투명성)이 있다.
  • ③ 데이터를 여러 위치에 분산하여 저장하고 관리하므로 대용량 처리 시 응답 속도를 단축할 수 있다.
  • ④ 분산 환경 구조상 데이터 정합성과 무결성을 제어하기 위한 소프트웨어 아키텍처가 단순해져 시스템 구축 비용이 크게 절감된다.
상세 해설
정답은 ④입니다.
  • ①, ②, ③ (옳은 선지): 분산 데이터베이스가 가지는 고유의 장점들(지역 독립성, 생존성 확보, 부하 분산)을 정확히 나열했습니다.
  • ④ 아키텍처가 단순해져 시스템 구축 비용이 절감 (틀린 선지): 분산 데이터베이스는 여러 하드웨어 노드에 쪼개진 데이터들의 실시간 정합성과 동기화를 맞춰야 하므로, 제어 로직이 극도로 복잡해지고 통신 오버헤드가 발생하며 관리 및 구축 비용이 훨씬 크게 증가한다는 치명적인 단점이 있습니다.
Q10. 데이터 모델링의 세 가지 단계인 개념적, 논리적, 물리적 데이터 모델링에 대한 매칭 중 가장 올바르지 않은 것은?
  • ① 개념적 데이터 모델링: 사용자의 요구사항을 분석하여 핵심 엔터티를 도출하고 전체적인 뼈대(ERD)를 도출하는 추상화 단계이다.
  • ② 논리적 데이터 모델링: 특정 RDBMS 제품에 종속되지 않은 상태에서 상세 속성 정의, 식별자 확정, 정규화를 수행하는 구조 정립 단계이다.
  • ③ 물리적 데이터 모델링: 구체적인 DBMS 제품(Oracle, MySQL 등)의 물리적 저장 구조, 인덱스, 역정규화 등을 설계하는 구현 단계이다.
  • ④ 개념적 모델링 단계에서 성능 최적화를 위한 인덱스 분산 설계와 파티셔닝 전략을 완성해야 논리적 무결성이 확보된다.
상세 해설
정답은 ④입니다.
  • ①, ②, ③ (옳은 선지): 개념(추상화/ERD), 논리(정규화/DBMS 독립), 물리(성능/DBMS 종속) 모델링의 정석적인 정의 문장입니다.
  • ④ 개념적 모델링 단계에서 인덱스 및 파티셔닝 전략 완성 (틀린 선지): 물리적인 디스크 구조, 인덱스 매핑, 파티셔닝 분산 전략 등은 모델링의 가장 마지막 단계인 물리적 데이터 모델링 단계에서 검토되고 확정되는 사항입니다. 초기 개념 단계에서는 비즈니스 요구사항 해석에 초점을 맞춥니다.

Q11. 다음 중 DDL(데이터 정의어) 명령어인 `TRUNCATE TABLE`과 DML(데이터 조작어) 명령어인 `DELETE FROM`의 차이점에 대한 설명으로 가장 올바르지 않은 것은?
  • ① `DELETE`는 테이블 내의 특정 행(Row)만 골라서 삭제할 수 있는 `WHERE` 절 조합이 가능하지만, `TRUNCATE`는 무조건 테이블 전체 데이터를 날려야 한다.
  • ② `DELETE`는 수행 시 시스템 로그(Undo/Redo)를 한 땀 한 땀 무겁게 남기므로 속도가 느리지만, `TRUNCATE`는 디스크의 스토리지 할당 공간(Extent) 자체를 무효화하여 속도가 대단히 빠르다.
  • ③ 두 명령어 모두 실행 후 데이터가 완전히 사라지더라도, 유저가 명시적으로 `ROLLBACK` 명령어를 입력하면 원래 상태로 완벽히 복구할 수 있다.
  • ④ `TRUNCATE`는 데이터만 삭제할 뿐 테이블 구조(Schema) 자체를 파괴하지는 않으므로 `DROP` 명령어와 구별된다.
상세 해설
정답은 ③입니다.
  • ①, ②, ④ (옳은 선지): DELETE(WHERE 가능, 로그 생성으로 느림)와 TRUNCATE(전체 삭제, 고속 처리, 구조 보존)의 실무적 차이점을 아주 정확하게 비교했습니다.
  • ③ 두 명령어 모두 ROLLBACK이 가능하다 (틀린 선지): `DELETE`는 DML이므로 트랜잭션 통제를 받아 롤백이 가능하지만, `TRUNCATE`는 **DDL 명령어**입니다. DDL은 실행되는 순간 내부적으로 **Auto Commit(묵시적 커밋)**이 발생하기 때문에, 수행 이후 유저가 아무리 롤백을 외쳐도 **절대 데이터를 복구할 수 없습니다.**
Q12. 아래 쿼리문과 같이 숫자와 문자가 혼합된 조건 연산을 수행할 때의 최종 출력 결과로 올바른 것은? (단, Oracle 환경 기준)

  • ② 300

Q13. 표준 SQL에서 지원하는 집계 함수(Aggregate Functions)의 NULL 처리 및 연산 원칙에 대한 설명 중 가장 올바르지 않은 것은?
  • ① `SUM(salary)` 연산 시, 특정 행의 `salary` 값이 NULL이면 해당 행을 연산 대상 집합에서 완전히 제외(무시)하고 합계를 낸다.
  • ② `AVG(salary)` 연산 시, NULL인 행은 분모(Count)와 분자(Sum) 계산에 모두 참여하지 않는다.
  • ③ 테이블의 전체 행 수가 10건이고 그 중 3건의 급여가 NULL일 때, `COUNT(*)`의 결과는 7건이고 `COUNT(salary)`의 결과는 10건이다.
  • ④ 만약 테이블에 데이터가 단 1건도 존재하지 않는 상태(빈 테이블)에서 `SUM(salary)`을 구하면 에러가 나지 않고 결과로 `NULL`을 반환한다.
상세 해설
정답은 ③입니다.

Q14. 표준 SQL 문법에서 제공하는 `NULLIF(A, B)` 함수의 논리 구조를 표준 `CASE` 문으로 가장 완벽하게 치환하여 표현한 것은?
  • ① `CASE WHEN A = B THEN A ELSE B END`
  • ② `CASE WHEN A = B THEN NULL ELSE A END`
  • ③ `CASE WHEN A IS NULL THEN B ELSE A END`
  • ④ `CASE WHEN A <> B THEN NULL ELSE B END`

  • `NULLIF(A, B)` 함수는 **"A와 B의 값이 같으면 NULL을 뱉고, 다르면 첫 번째 인자인 A를 리턴한다"**는 매커니즘을 가집니다.
  • 따라서 이를 CASE 문 조건식으로 완벽히 번역하면 `CASE WHEN A = B THEN NULL ELSE A END` 가 됩니다. ①번은 일반적인 분기 뼈대이며, ③번은 `NVL` 또는 `ISNULL` 함수의 구조입니다.
Q15. 아래 쿼리문과 같이 WHERE 절과 HAVING 절에 중복 조건이 기재되어 수행될 때, 데이터베이스 옵티마이저가 처리하는 논리 구조 및 성능 관점의 설명으로 가장 올바른 것은?
SELECT dept_id, AVG(salary) FROM emp WHERE dept_id IN ('10', '20') GROUP BY dept_id HAVING dept_id IN ('10', '20');
  • ① WHERE 절과 HAVING 절에 동일 조건이 중복 기재되었으므로 구문 분석 에러(Syntax Error)가 발생한다.
  • ② WHERE 절에서 먼저 10, 20번 부서 행만 필터링한 후 그룹화하므로, HAVING 절의 중복 조건은 아무런 부하를 주지 않는 공짜 쿼리이다.
  • ③ 논리적 순서상 WHERE 절이 먼저 부서 행을 걸러내어 메모리 버퍼 크기를 대폭 줄여주므로 성능상 가장 우수하며, HAVING 절에만 조건을 두는 것보다 유리하다.
  • ④ HAVING 절 조건은 그룹화가 완료된 후의 거대한 집계 전체를 대상으로 필터링하므로, WHERE 절을 삭제하고 HAVING 절만 남기는 것이 옵티마이저 튜닝상 훨씬 고속으로 작동한다.
상세 해설
정답은 ③입니다.
  • ① (틀린 선지): 중복 기재해도 에러가 나지 않고 정상 작동합니다.
  • ③ (옳은 선지): 동일 조건을 WHERE 절과 HAVING 절에 모두 쓸 수 있다면, 무조건 **WHERE 절에 작성하는 것이 압도적으로 유리**합니다. WHERE 절에서 먼저 10, 20번 부서가 아닌 수만 건의 행 데이터를 원천 커트해주므로, `GROUP BY` 연산 장치로 넘어가는 정렬 대상 데이터양이 확 줄어들기 때문입니다. HAVING 절에만 조건을 주면 전체 사원을 다 정렬한 뒤 마지막에 부서를 버리므로 성능 최악이 됩니다.
Q16. 아래 쿼리문과 같이 SELECT 절에 집계 함수와 일반 컬럼이 혼합되어 사용되었을 때 발생하는 현상으로 올바른 것은? (단, ANSI 표준 규격 기준)
SELECT emp_name, AVG(salary) FROM emp;
  • ① 전체 사원의 이름 옆에 전체 평균 급여 수치가 동일하게 복사되어 정상 출력된다.
  • ② `GROUP BY` 절이 누락되었으므로 "단일 그룹의 그룹 함수가 아닙니다" 라는 문법 에러를 발생시키며 쿼리가 실패한다.
  • ③ 에러 없이 수행되나 `emp_name` 컬럼의 첫 번째 행 데이터 1건만 임의 출력된다.
  • ④ `AVG` 함수가 자동으로 단일 행 함수로 형변환되어 각 사원의 급여 자체가 출력된다.
상세 해설
정답은 ②입니다.
  • 표준 SQL 문법에서 `SUM`, `AVG` 같은 다중 행 집계 함수를 `GROUP BY` 절 없이 SELECT 절에 단독으로 쓰면 테이블 전체를 '통짜 1개 그룹'으로 인지합니다.
  • 결과로 무조건 **단 1줄(Row)**만 나와야 하는데, 그 옆에 묶이지 않은 일반 컬럼인 `emp_name`(사원이 100명이면 100줄 출력 요구)을 나란히 적어버리면 행의 균형이 깨집니다.
  • 따라서 데이터베이스는 **"단일 그룹의 그룹 함수가 아닙니다 (ORA-00937)"** 에러를 터트리며 실행을 거부합니다. (이러한 구조를 깨지 않고 옆에 나란히 붙이려면 일반 그룹 함수가 아닌 윈도우 함수 `AVG(salary) OVER()` 구문을 사용해야 합니다.)
Q17. ANSI 표준 조인 기법 중 `USING` 조건절을 적용하여 코딩할 때의 문법적 제약 원칙으로 가장 올바르지 않은 것은?
  • ① `USING` 절에 지정하는 조인 기준 컬럼은 반드시 두 테이블 간에 컬럼명이 완벽히 동일해야 한다.
  • ② `FROM emp e JOIN dept d USING (e.dept_id = d.dept_id)` 처럼 괄호 내부에 등호 연산자와 별칭을 명시해야 매칭된다.
  • ③ `USING` 절의 기준 컬럼은 SELECT 절에서 출력할 때 앞에 테이블 소유격 식별자(Prefix)를 붙여 표기할 수 없다.
  • ④ 한 번에 2개 이상의 복합 컬럼을 묶어서 조인 기준으로 삼고자 한다면 `USING (col1, col2)` 형태로 콤마 분리 기재가 가능하다.
상세 해설
정답은 ②입니다.
  • ①, ③, ④ (옳은 선지): USING 절의 철칙들입니다. 이름이 같아야 하고, 쉼표로 다중키 지정이 가능하며, SELECT 절 출력 시 별칭 접두사(Prefix)를 붙이면 식별자 에러가 터집니다.
  • ② 내부 식별자 및 연산자 명시 (틀린 선지): `USING` 절은 이름이 같은 컬럼을 명사 형태로 콕 집어주는 구문이므로 괄호 안에 연산자 기호(`=`)나 테이블 Alias를 적지 않고, `USING (dept_id)` 처럼 순수 컬럼 이름만 담백하게 던져야 합니다. 연산식을 쓰는 구조는 `ON` 절의 문법입니다.
Q18. 아래 SQL문과 같이 `WHERE` 절 조건에 인라인 뷰 서브쿼리가 다중 컬럼 형태로 묶여 비교 연산이 수행될 때의 매커니즘 특징으로 올바르지 않은 것은?
SELECT * FROM emp WHERE (dept_id, job_id) IN ( SELECT dept_id, job_id FROM dept_spec WHERE spec_grade = 'A' );
  • ① 메인 쿼리의 컬럼 순서 및 개수와 서브쿼리 SELECT 절의 컬럼 순서 및 개수가 완벽히 일치해야 문법이 성립한다.
  • ② 이 연산은 괄호 안의 컬럼들이 각각 따로 독립적으로 필터링 되는 것이 아니라, 두 컬럼의 조합 쌍(Pair) 단위로 동시에 일치하는지 평가한다.
  • ③ 다중 컬럼 서브쿼리는 SQL Server(MS SQL) 환경에서도 표준 아키텍처로 완벽히 지원되므로 이식성이 가장 우수한 구문이다.
  • ④ 오라클 환경에서 주로 지원되는 강력한 서브쿼리 문법 중 하나이다.
상세 해설
정답은 ③입니다.
  • ①, ②, ④ (옳은 선지): 다중 컬럼 서브쿼리(Multi-Column Subquery)의 특징입니다. 개수/타입 짝이 맞아야 하고, 각자 따로 노는 게 아니라 쌍(Pair) 단위로 완벽히 결합 징검다리를 확인합니다.
  • ③ SQL Server 환경에서도 완벽히 지원 (틀린 선지): 안타깝게도 다중 컬럼 서브쿼리 괄호 묶음 연산 `WHERE (col1, col2) IN (...)` 구조는 오라클 등에서는 아주 잘 돌지만, SQL Server(MS SQL)에서는 문법적으로 지원하지 않는 경우가 많아 에러가 납니다. (SQL Server에서는 주로 `EXISTS`나 일반 `JOIN` 구조로 바꾸어 작성해야 합니다.)
Q19. 아래와 같이 메인 쿼리 WHERE 절에 `NOT IN` 연산자가 사용되었고, 서브쿼리의 결과 집합 내에 `NULL` 값이 한 건이라도 포함되어 있을 때 발생하는 쿼리 최종 실행 결과 현상은?
SELECT * FROM emp WHERE dept_id NOT IN (SELECT dept_id FROM dept WHERE region = 'JEJU'); -- 💡 가정: JEJU 지역 부서 중 dept_id가 NULL인 행이 1건 존재함.
  • ① NULL 행을 제외한 나머지 부서 코드와 일치하는 사원들만 정상 출력된다.
  • ② 메인 쿼리의 전체 결과가 무조건 **0건(Empty Set)**으로 아무것도 나오지 않는다.
  • ③ 런타임 데이터 타입 변환 오류가 발생하며 시스템이 다운된다.
  • ④ 메인 테이블의 전체 사원 데이터가 조건 없이 100% 전부 출력된다.
상세 해설
정답은 ② 메인 쿼리의 전체 결과가 0건으로 출력됨입니다.
  • SQLD 과목 전체에서 가장 빈번하게 수험생의 뒤통수를 치는 최고 고난도 단골 메커니즘 앤서입니다.
  • `NOT IN (10, 20, NULL)` 연산은 논리적으로 풀어서 쓰면 `dept_id <> 10 AND dept_id <> 20 AND dept_id <> NULL` 과 같습니다.
  • 앞서 누차 강조했듯 **NULL과의 비교 연산(`<> NULL`)은 무조건 결과가 UNKNOWN(거짓 취급)**이 되며, 전체 조건이 `AND`로 묶여있기 때문에 단 한 조각이라도 거짓이 되면 **전체 WHERE 문이 통째로 거짓**이 됩니다.
  • 따라서 메인 테이블에 어떤 훌륭한 데이터가 들어있든 간에 전부 매칭 실패 처리되어 결과가 단 1줄도 나오지 않는 빈 화면(0건)이 됩니다. 이를 막으려면 서브쿼리 내에 `WHERE dept_id IS NOT NULL` 방어벽을 반드시 쳐야 합니다.
Q20. 집합 연산자 중 차집합을 구해주는 `MINUS` (Oracle) 연산자와 동일한 기능을 수행하도록 표준 SQL 규격으로 명시된 연산자 명칭은?
  • ① SUBTRACT
  • ② EXCEPT
  • ③ LESS
  • ④ REMOVE
상세 해설
정답은 ② EXCEPT입니다.
  • 차집합을 나타내는 오라클 전용 키워드는 `MINUS` 이지만, **ANSI 표준 규격 및 SQL Server 등에서 사용하는 표준 명칭은 `EXCEPT`** 입니다. 두 키워드는 이름만 다를 뿐 중복 제거 및 정렬을 수반하는 내부 집합 매커니즘은 완전히 동일합니다.
Q21. 윈도우 함수 중 현재 행을 기점으로 파티션 내에서 정렬된 이전 행들의 값을 당겨오는 `LAG` 함수와 다음 행들의 값을 밀어오는 `LEAD` 함수에 대한 설명으로 올바르지 않은 것은?
  • ① `LAG(col, 2)` 라고 명시하면 현재 행보다 정확히 2칸 위에 존재하는 행의 해당 컬럼 값을 가져온다.
  • ② `LEAD(col, 1, 0)` 처럼 3번째 인자에 값을 주면, 다음 행이 존재하지 않는 마지막 단계(Boundary) 도달 시 NULL 대신 지정한 기본값(0)을 채워 출력한다.
  • ③ 두 함수 모두 파티션 내의 데이터 흐름 순서가 중요하므로 `OVER` 절 내부에 `ORDER BY` 구문이 필수로 수반되어야 정상 작동한다.
  • ④ 이 함수들은 행 간의 비교를 수행하므로 사용하려면 반드시 `ROWS BETWEEN` 프레임 영역 제한 구문을 끝에 결합해 주어야 한다.
상세 해설
정답은 ④입니다.
  • ①, ②, ③ (옳은 선지): LAG/LEAD 함수의 오프셋 지정, 3번째 대체인자 활용법, 정렬(ORDER BY) 필수 제약 조건을 아주 훌륭하게 기술했습니다.
  • ④ 프레임 제한 구문을 결합해야 한다 (틀린 선지): `LAG`와 `LEAD` 함수는 행과 행의 절대적인 오프셋 위치(위/아래 칸수)를 직접 지명하여 스캔하는 함수이므로, `ROWS BETWEEN` 같은 프레임 윈도우 범위 제약 구문을 절대로 붙일 수 없으며 붙이면 문법 오류가 발생합니다.
Q22. 계층형 질의문에서 루트 노드(최상위 부모) 데이터를 필터링하기 위해 사용하는 `START WITH` 절에 대한 설명으로 가장 올바른 것은?
  • ① `START WITH` 절 조건에는 오직 주식별자(PK) 컬럼 조건만 올 수 있다.
  • ② `START WITH` 절에 명시된 조건에 부합하는 행은 계층 트리 구조에서 무조건 `LEVEL` 수치가 0으로 셋팅된다.
  • ③ `START WITH` 절 조건은 서브쿼리를 포함할 수 없으므로 무조건 단일 상수로만 지정해야 한다.
  • ④ `START WITH` 절 조건을 생략하는 경우, 테이블 내의 모든 행(Row)을 각각 개별적인 최상위 루트 노드로 간주하여 트리 전개를 시도한다.
상세 해설
정답은 ④입니다.
  • ①, ③ (틀린 선지): START WITH 절에는 일반 컬럼, 서브쿼리 등 복잡한 조건식을 자유롭게 작성할 수 있습니다.
  • ② 수치 세팅 오류 (틀린 선지): 최상위 시작점의 LEVEL은 0이 아니라 1부터 시작합니다. 자식으로 갈수록 2, 3으로 늘어납니다.
  • ④ 조건을 생략하는 경우의 동작 (옳은 선지): START WITH 절은 문법적 필수가 아니므로 생략 가능합니다. 생략하면 테이블 전체 행을 모조리 스타트 루트 노드로 선언해 트리를 전개하므로 엄청난 양의 데이터가 중복 출력됩니다.
Q23. 다음 그룹 함수 중, 소계나 총합계 연산이 수행되어 시스템이 가짜로 만들어낸 행(Subtotal Row)인지 아니면 실제 테이블에 들어있던 진짜 데이터 행인지를 판별하여 가짜 행이면 1, 진짜 행이면 0을 리턴해주는 판별용 함수는?
  • ① GROUPBY()
  • ② GROUPING()
  • ③ GROUP_NUMBER()
  • ④ IS_SUBTOTAL()
상세 해설
정답은 ② GROUPING()입니다.
  • `ROLLUP`이나 `CUBE`를 돌리면 합계 행의 컬럼값들이 `NULL`로 출력되는데, 이게 진짜 테이블에 NULL이 박혀있던 건지 소계 행이라 비어있는 건지 구별이 안 됩니다.
  • 이때 `GROUPING(컬럼)` 함수를 적용하면, 소계 연산 때문에 인위적으로 생성된 NULL 셀인 경우 정확히 숫자 `1`을 리턴해 줍니다. 개발자는 이를 `CASE` 문과 엮어 `1`일 때 '총합계'라는 글자로 예쁘게 치환할 수 있습니다.
Q24. 다음 중 트랜잭션을 강제로 완전히 종료시키지 않고, 오류 발생 시 복구 지점을 제공하기 위해 사용하는 세이브포인트(`SAVEPOINT`)의 특징으로 가장 올바르지 않은 것은?
  • ① 한 트랜잭션 내에 서로 다른 이름으로 여러 개의 `SAVEPOINT`를 동시 다발적으로 지정할 수 있다.
  • ② `ROLLBACK TO 세이브포인트명;` 구문을 실행하면 해당 지점 이후에 실행된 DML 명령어만 취소되고 그 이전 작업은 임시 보존된다.
  • ③ 동일한 이름으로 `SAVEPOINT`를 한 트랜잭션 내에 중복 선언하면 먼저 선언된 올드 지점은 파기되고 최신 지점만 유효하게 남는다.
  • ④ `ROLLBACK TO 세이브포인트명;` 구문이 완벽하게 성공하면, 해당 저장 지점 이전의 모든 데이터 작업들이 데이터베이스에 즉시 영구 커밋(COMMIT) 처리된다.
상세 해설
정답은 ④입니다.
  • ①, ②, ③ (옳은 선지): 다중 세이브포인트 운영 룰, 부분 취소 메커니즘, 명칭 중복 시 최신 덮어쓰기 법칙을 정확하게 기술했습니다.
  • ④ 저장 지점 이전 작업들이 영구 커밋 처리된다 (틀린 선지): `ROLLBACK TO` 명령어는 특정 시점 이후의 작업을 **'일부 취소(롤백)'** 시켜주는 제어 장치일 뿐입니다. 취소하고 남은 이전 단계의 데이터들은 여전히 **메모리 버퍼에 붕 떠 있는 임시 상태(Uncommitted)**로 유지됩니다. 최종적으로 영구 반영하려면 유저가 명시적으로 **`COMMIT`** 명령어를 한 번 더 내려주어야 합니다.
Q25. 다음 중 인덱스를 조건절에 명시했음에도 불구하고, B-Tree 인덱스의 정렬 구조가 파괴되거나 인덱스 헤더를 타지 못해 전체 테이블 풀 스캔(Full Table Scan)이 발생하는 최악의 SQL 코딩 패턴에 해당하지 않는 것은?
  • ① `WHERE emp_name LIKE '이%'` (와일드카드를 뒤에 배치)
  • ② `WHERE salary * 12 > 50000` (인덱스 컬럼 자체를 수식으로 산술 가공)
  • ③ `WHERE NVL(dept_id, '00') = '10'` (인덱스 컬럼을 내장 함수로 감싸서 변형)
  • ④ `WHERE job_id IS NULL` (일반적인 단일 B-Tree 인덱스 환경에서 NULL 여부 검색)
상세 해설
정답은 ①입니다.
  • ②, ③, ④ (틀린 선지): 컬럼을 수식 계산하거나 함수로 가공하면 인덱스가 깨져 풀 스캔을 탑니다. 또한 일반적인 B-Tree 인덱스는 NULL 값을 지도에 저장하지 않으므로 `IS NULL` 검색 시 인덱스를 타지 못하고 풀 스캔을 유발합니다.
  • ① LIKE '이%' (옳은 선지 - 풀 스캔 안 탐): 와일드카드 기호(`%`)가 문자열의 **맨 뒤(Trailing)**에 배치되면, '이'로 시작하는 정렬 구역을 인덱스 나무에서 바로 찾아 들어갈 수 있으므로 정상적으로 고속 인덱스 범위 스캔(Index Range Scan)이 작동합니다. (반면 `%이` 처럼 앞에 오면 풀 스캔을 탑니다.)
Q26. 관계형 데이터베이스의 옵티마이저(Optimizer) 중, 통계 정보가 없던 과거 시절에 사전 정의된 우선순위 규칙(예: PK 조회가 1순위, 전체 풀 스캔이 맨 꼴찌 순위)에만 전적으로 의존하여 경로를 수립하던 구형 엔진 명칭은?
  • ① 규칙 기반 옵티마이저 (RBO, Rule Based Optimizer)
  • ② 비용 기반 옵티마이저 (CBO, Cost Based Optimizer)
  • ③ 통계 기반 옵티마이저 (SBO, Statistic Based Optimizer)
  • ④ 예측 기반 옵티마이저 (PBO, Predictive Based Optimizer)
상세 해설
정답은 ① 규칙 기반 옵티마이저 (RBO)입니다.
  • 데이터의 양이나 디스크 블록 수를 전혀 보지 않고, 오직 시스템 내부에 미리 정해진 15가지 고정 규칙 순위에만 의존하여 길을 찾던 과거의 구형 엔진을 **RBO(규칙 기반 옵티마이저)**라고 부릅니다. 현재 대다수 모던 DB는 **CBO(비용 기반)**를 씁니다.
Q27. 다음 중 테이블 스키마 구조 변경을 위한 DDL 명령어인 `ALTER TABLE` 구문을 활용해 수행할 수 없는 작업은?
  • ① 기존 테이블에 새로운 컬럼을 추가하기 (`ADD`)
  • ② 기존 특정 컬럼의 데이터 타입 크기를 확장하기 (`MODIFY`)
  • ③ 기존 특정 컬럼에 걸려있던 제약조건(예: NOT NULL)을 완전히 제거하기 (`DROP / MODIFY`)
  • ④ 테이블 내부의 특정 데이터 행(Row)의 오타를 수정하기 (`UPDATE`)
상세 해설
정답은 ④입니다.
  • ①, ②, ③ (옳은 선지): 테이블의 껍데기(구조, 제약조건)를 개조하는 작업은 DDL인 `ALTER TABLE`을 통해 완벽히 제어합니다.
  • ④ 데이터 행의 오타 수정 (틀린 선지): 테이블 내부에 실존하는 알맹이 데이터 값을 수정하는 행위는 DDL이 아닌 **DML 명령어인 `UPDATE ... SET`** 구문을 사용해야 합니다. 뼈대(DDL)와 알맹이(DML)를 구분하는 기초 변별력 문제입니다.
Q28. 조인 수행 원리 중 두 테이블의 조인 컬럼을 기준으로 각각 데이터를 정렬(Sort)한 후, 정렬된 두 집합을 위에서부터 차례대로 스캔하며 매칭하는 고속 조인 아키텍처 명칭은?
  • ① 중첩 루프 조인 (Nested Loops Join)
  • ② 정렬 병합 조인 (Sort Merge Join)
  • ③ 해시 조인 (Hash Join)
  • ④ 인덱스 스캔 조인 (Index Scan Join)
상세 해설
정답은 ② 정렬 병합 조인 (Sort Merge Join)입니다.
  • 조인 컬럼 양쪽 집합을 메모리(Sort Area)에서 먼저 이쁘게 **정렬(Sort)**해 둔 다음 바둑판 맞추듯 **병합(Merge)** 전개하는 방식을 정렬 병합 조인이라고 합니다. 조인 조건에 인덱스가 없거나 범위 조건(`<, >`) 조인 시 대용량 처리에서 성능을 발휘합니다.
Q29. 데이터베이스 성능 튜닝의 핵심인 '해시 조인(Hash Join)'의 특징으로 가장 거리가 먼 것은?
  • ① 두 테이블 중 크기가 작은 테이블(Build Input)을 메모리에 올려 해시 테이블을 먼저 생성하는 메커니즘을 가진다.
  • ② 해시 함수를 이용해 주소를 직접 타격하므로 동등 조인(`=`) 조건에서만 사용할 수 있고, 부등호 조건 조인에서는 사용할 수 없다.
  • ③ 대용량 데이터 조인 시 중첩 루프 조인(NL)보다 대단히 고속으로 동작하지만, 메모리(Hash Area) 공간이 부족하면 디스크 자원을 써서 성능이 저하될 수 있다.
  • ④ 조인 컬럼에 반드시 사전 생성된 인덱스(Index)가 수반되어야만 옵티마이저가 해시 조인 경로를 수립할 수 있다.
상세 해설
정답은 ④입니다.
  • ①, ②, ③ (옳은 선지): 해시 조인의 핵심 원리(작은 테이블로 빌드 테이블 생성, 등가 조인에서만 동작, 인덱스 없는 대량 조인 최강자, 메모리 고갈 시 디스크 부하)를 아주 깊이 있게 정확히 기술했습니다.
  • ④ 반드시 사전 생성된 인덱스가 수반되어야 함 (틀린 선지): 해시 조인은 인덱스를 타는 조인이 아니라, 런타임에 메모리에 해시 맵을 동적으로 생성해 직접 타격하는 방식입니다. 따라서 조인 컬럼에 인덱스가 단 한 개도 존재하지 않을 때, 대용량 데이터를 고속으로 조인하기 위해 옵티마이저가 내리는 최고의 선택지가 바로 해시 조인입니다.
Q30. 오라클에서 가로로 나열된 여러 개의 컬럼 인자들 중 '가장 큰 값(최대값)'을 한 줄(Row) 내에서 찾아 반환해 주는 단일 행 함수 명칭은?

  • ① MAX()
  • ② GREATEST()
  • ③ LEAST()
  • ④ HIGHEST()

점수: 0 점
